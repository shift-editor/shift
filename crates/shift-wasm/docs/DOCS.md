# shift-wasm

<!-- reviewed: 2026-10-31 review-every: 90d -->

Runs shift-font's rules in the editor through WebAssembly, so the editor calls the same Rust the workspace and export use instead of a TypeScript copy. `crates/shift-wasm` is the Rust side; `packages/wasm` (`@shift/wasm`) builds it and ships the module to TypeScript.

## Architecture Invariants

- **One implementation.** Each export calls shift-font code that native callers also use: anchor kinds from fontir's `AnchorKind::new`, `anchor_propagation::compiled_anchors`, `anchor_attachment::follow_anchors`, and the variation evaluators (`AxisMappingBasis::evaluate`, `map_location_with_bases`, `InterpolationBasis::weights_at`). This crate only converts between numbers and those types. A rule that needs logic here is a rule that belongs in shift-font.
- **Synchronous.** The module is embedded in `@shift/wasm` as base64 and instantiated with `initSync` at import, so computeds and render paths call it directly. Nothing awaits, fetches, or needs a bundler plugin; desktop, vitest, and the SDK import it the same way. The engine is the exception: `@shift/wasm/engine` ships `shift_wasm_bg.wasm` as a file and compiles it during its (dynamic) import, fetched in the renderer and read from disk under Node; calls after the import are synchronous. **WHY:** decoding its 3.8 MB of base64 cost about 60 MB under Node and compiled on the main thread.
- **Built, never committed.** `packages/wasm/src/generated/` and `src/generated-engine/` are gitignored and built like the native addon: `@shift/wasm#build` is a turbo task over the Rust sources that builds the two modules the app loads; `build:native` runs it, and tests and desktop builds depend on it. Typecheck depends on `@shift/wasm#types` instead (`build.mjs --types`), which writes only each variant's `shift_wasm.d.ts` and `module.d.ts` from a debug build without wasm-opt. The release build writes the same declarations; `InitOutput` is sorted in both, because its members follow the module's export order, which differs between debug and release. WHY: rustc's output depends on the build host (Cargo hashes `rustc -vV`, host line included, into symbol names, which decides data layout), so a module built on macOS never matches one built on Linux, and a committed copy could not be checked against a fresh build.
- **Pinned toolchain.** wasm-bindgen is pinned exactly (`=0.2.121`); the build script refuses a CLI that does not match `Cargo.lock`. wasm-opt is the npm `binaryen` package, pinned exactly as a devDependency of `@shift/wasm` and run through Node from the package's own `bin`, never from PATH, with explicit features. It only shrinks the module, so it runs only with `SHIFT_WASM_OPT=1`, which the Nightly, release and perf workflows and `pnpm profile:build` set; local builds and CI tests skip it, about 20 s per build. The Cargo home path that panic messages embed is remapped, so the module carries no machine's paths. Cargo passes workspace crates as paths relative to the checkout, so the checkout is not remapped, which keeps RUSTFLAGS, and so every crate's fingerprint, the same in every checkout.
- **Numbers across the boundary.** Hot calls take and return `Float64Array`s, with no per-call objects. **CRITICAL**: hot calls are `#[pack::interface]` traits (`Anchors`, `Axes`, `Decomposition`, `Drag`, `Geometry`, `Variation`, `EngineEdits`, `EngineReads`, `SvgPaths`), each answered by one `<trait>Request(method, input)` export, and their values are `#[derive(Pack)]` types, shift-font's behind its `pack` feature (`crates/pack`). The editor's side, a class per trait and each type's schema, reader and writer, is generated from them into `packages/wasm/src/generated-protocol/` (`@shift/wasm/protocol`, gitignored) by `packages/wasm/scripts/protocol.mjs` during every wasm build. Never hand-write a packer: a field order typed out twice drifts silently, because reading past the end yields zeros rather than an error. Anchor names are interned once (`internName`/`nameOf`) and travel as ids. A location travels as numbers in the font's axis order, NaN for a missing coordinate. Every structured value, cold ones such as `AnchorKind` included, is a pack type; the only plain `wasm_bindgen` exports are calls that pass typed arrays or JavaScript functions as they are (`blendSourceValues`, the engine's session calls), so `shift_wasm.d.ts` is generated, not hand-written.
- **Shaping runs in the engine module, over the session's own font.** The `engine` feature also builds shift-shape, HarfRust and the shaper-font compile (shift-shaper-font: fea-rs and fontbe), and `EngineReads.shapeParagraphs` answers from the session: it compiles a shaper font from the session's font (`EngineSession::shaper_font_source`) when text is first shaped, and again before the next shape after an edit whose impact touches the glyph directory or the axes and their mappings (`TextShaping::INPUTS`); a rewound or cancelled edit marks it the same way for what its applies changed. The compile carries forward (shift-shaper-font's `ShaperFontState`): it runs only when a compile input changed, so adding a glyph the feature source does not name, and that has no `GDEF` class, appends it to the shaper's glyph order instead; feature code with errors keeps the last font. The session reads the store once per answer (shift-engine's `RecordCache`): glyph data's category per name and codepoints, and the attaching anchors of each layer it has not loaded, for glyph records and the shaper's source alike. Shaped glyphs cross by `GlyphId`, in the engine module's name table. Each edit, stage, undo and redo carries its `FontChangeImpact` bits (`EngineEditLayers.impact`, `EngineStage.impact`); the window's engine keeps one revision per shift-font `FontChangeFlag` (`FontEngine.revision`), whose list TypeScript takes from the generated `FontChangeFlagSchema`, and shaped text tracks the flags `EngineReads.shapingInputs` names. A paragraph that cannot be shaped comes back with its reason (`ShapedParagraph::Unshapable`), including when the store's reader cannot answer or the font cannot make a shaper font. **WHY:** one memory, so text layout can read the live font with no copy between modules; the shaping module it replaces cost a second instance, its own name table, and a copy of every glyph's shaper source per registration. Merging made the engine module 2.55 → 5.39 MB (0.87 → 1.87 MB gzip) and its first compile 2.2 → 4.4 ms under Node 24, while the 3.18 MB shaping module, embedded as about 4.2 MB of base64, went away. A panic in fea-rs or HarfRust now ends the editing session, so `shift-shaper-font` keeps returning errors rather than panicking. The generated classes import no module; each entry point (`index.ts`, `engine.ts`) builds its classes over its own module's request exports and name table, so loading one module never pulls in another.
- **The editing engine is a module of its own, loaded when a font opens for editing.** The `engine` feature builds shift-engine's `EngineSession` into `src/generated-engine/`, loaded by `@shift/wasm/engine` and wrapped by the editor's `lib/wasm/engine.ts` (`loadEngine`, `EngineSession`). It is the same session the native workspace runs. Intents cross as shift-font's own `FontIntent` values, packed: the editor sends them with `EngineEdits.hold` (`engine_edits.rs`), and the `engineApply`, `engineStage` or `enginePreview` call that follows takes them. The font-level records an apply, undo or redo changed cross packed too, through `EngineEdits.replacement`, as shift-wire's `FontReplacement`: the same shape the native workspace's echo carries, so the window reads one type from both. Its `glyphChanges` holds the records of the glyphs the edit changed, built by the session in the same call (`EngineSession::glyph_record_changes`), so an unsaved rename or codepoint change shows its new category in the frame it is made. Touched layers come back as values, with their structure only when the edit changed it (`EngineLayer.structure` is null otherwise), and then with each contour the edit kept sent by id alone (`KeptContour`), read against the structure the edit started from. **WHY:** building a 50,000-point glyph's structure as objects cost more than the edit; a nudge of all its points took 51.6 ms, and an added point 38 ms in the editor. A `setPositions` intent's positions cross as one copied `Float64Array` (`#[pack(numbers)]`). The change set an edit returns for persisting is compacted (`FontChangeSet::compact`): a layer change that only moved values carries the values, not the layer twice (7.8 to 1.9 ms to encode, 7 MB to 1.8 MB), and the workspace rebuilds it against its own layer (`FontWorkspace::persist_compact_change_set`). Layers load through shift-engine's `StoreReader` request protocol: the session's `LayerSource` is a `StoreReaderClient` that encodes each request in Rust and calls the one `StoreRequest` function the editor passes in, which forwards the numbers and blobs unchanged to the preload's native `LayerReader.request` and returns its reply. JavaScript is only a pipe, so no TypeScript copy of the requests exists to drift; ids travel with each message (`pack::CarriedNames`, the last blob), since the engine and the native reader share no name table. The request must not call back into the engine. A gesture keeps one edit open across frames: `engineRewindEdit` puts the session back where the edit began, and `engineStage` applies the frame's intents without building font-level records, which are built once, by `engineApply`, when it commits.
- **The document's scene is in the engine session, beside the font.** The session holds shift-engine's `Scene`: the window reads it through `StoreReader.scene_nodes` and passes it to `engineOpen` (with none, the session's scene is empty, for reading a font's records alone). `EngineReads.sceneNodes` returns each node with its revision and its items' revision, which change only when the node, or a text run's items, may have, so the editor keeps what it built from an unchanged node without comparing them. The editor sends scene intents with `EngineEdits.holdScene`, and the `engineApply` or `engineStage` that follows applies them after any held font intents, in the same open edit, so one undo step and one persisted change set carry both. An edit that changed the scene sets `FontChangeImpact::SCENE` in its impact, so the window bumps `revision("scene")`. `engineBeginEdit(handle, page)` records the page the window shows as where the edit was made; `engineEndEdit(handle, recording)` closes it as an undo step (`"undoable"`) or keeps it without one (`"unrecorded"`), and returns a `CompactDocumentChangeSet` (font and scene) to persist. After an undo or redo, `EngineEdits.replayedLocation` hands back where its edit was made: the page and the glyphs and nodes it changed. `EngineReads` answers the scene in tree order (`sceneNodes`, `scenePages`, `pageNodes`, `sceneNode`). A session with no engine (a preview, an in-memory session) holds the same scene in the default module (`scene.rs`, `Scenes`), with nothing persisted.
- **The editor reads the font from the engine, in flat hot calls.** `engine_reads.rs`'s `EngineReads` answers the font's axes, master sources (with their metric values), kerning and glyph records as shift-font's own types (`axes`, `sources`, `kerning`, `glyphRecords`), which the editor reads when it opens a document and which the native workspace no longer serves it; kerning (`kerningRun` for a whole run of pairs, `kerningPairs` for which authored pair applies or an edit changes, `kerningPairsNaming`, `missingKerningOrigin`) and source metrics between masters (`sourceMetricsAt`); and the per-frame variation reads, the weights of every interned source set at a design location in one read (`sourceSetWeights`, which a frame reads once per location and each glyph takes its set's row from) or of every weight set of a Slug atlas at an external location (`atlasWeights`), and axis mapping (`designLocation`, `externalLocation`), all from the session's font, an open edit included, through `engineReadsRequest(handle, method, input)`; `@shift/wasm/engine`'s `engineReads(handle)` binds a class to one session. Glyph records come in name order (shift-font's `GlyphRecords`), and an edit that adds, removes or renames a glyph also carries the font's new glyph order, as ids. A glyph record needs two answers the session's font cannot give, which it asks the store's reader for through `StoreReader`: the component bases of a glyph whose layers it has not loaded (`component_bases`), and glyph data's categories (`glyph_data_categories`), whose Glyphs data stays native rather than ship in the module; the category rule itself is shift-font's (`ir::glyph_category`). `shapeParagraphs` reads what the shaper font compiles from the same way, asking the store which unloaded layers carry an anchor marks attach to (`attaching_anchor_layers`), since a base's or ligature's GDEF class depends on it. The session derives each source set's interpolation basis and the font's compiled axis mappings from its own font when a read first needs them (`FontVariation`), and keeps them with the axes, axis mappings and source locations they came from: a read whose font has other ones derives them again, so no edit, undo, rewind or cancel needs to drop them. The trait and its types are declared with the `engine-protocol` feature alone, so the editor's side generates from a check that builds no session; it stays out of the default build, which would otherwise link shift-wire (and napi's symbols wherever another crate turns napi on). The hot reads name glyphs, sources and source sets by numbers the session interns once each (`engineGlyphNumbers`, `engineSourceNumbers`, `engineSourceSetNumber`), and the editor's `EngineSession` caches them; the records carry ids as names in the module's name table.
- **Variation without an engine is stateless.** A font the window does not edit (a preview, a retained source, a memory session: the SDK, the sandbox) has no session to hold its axes and bases, so `variation.rs`'s `Variation` calls carry them whole each time: `interpolationWeights`, `evaluateVariation`, `mapLocation`, `unmapLocation`, and `atlasWeights`, which maps a Slug atlas's location once and evaluates every weight set in one call (the open document's atlas uses it only while its engine is closed, with the bases from the native atlas descriptor). The editor's `Font` takes a `VariationReader` (`lib/wasm/variation.ts`): `EngineVariationReader` for the open document, which asks the engine and falls back to the stateless calls while it is closed, and `StatelessVariationReader` otherwise; `Designspace` and `Glyph` evaluate through it, and neither registers anything with the module.

## Key Types

- **`AnchorKind`** — an anchor's role read from its name, as a packed tagged union.
- **`VariationReader`** — what a `Font` evaluates its variation with: the engine's reads for the open document, the stateless `Variation` calls otherwise.
- **`pack::Pack`** — a value that packs into numbers: `read` and `write`, derived with `#[derive(Pack)]`. Fields cross in declaration order; a list is its length then its items, an optional value a flag then the value, a name its interned id, an enum its variant index (a string in TypeScript, where an unknown index throws). Locations are plain numbers in the font's axis order.
- **`#[pack::interface]` traits** — one per module area; a method crosses as its index in the trait, then its arguments in order. The macro writes `<trait>_request(target, method, input, blobs, names)`, which the module's `<trait>Request(method, numbers, blobs)` export calls on the type that answers it (`blobs.rs`), and a Rust `<Trait>Client` over a `pack::Transport`. A `pack::Bytes` value crosses as one blob beside the numbers, which hold its index in the message's blob list; a reply's blobs wait in the module until the transport calls `takeReplyBlobs`, which it does only for a reply that reads bytes, so a per-frame call without bytes allocates no list. A method returning `Result<T, E>` (a flag set for `Ok`, then the value or the error) returns `T` in TypeScript and throws `@shift/pack`'s `PackError`, carrying the error as its generated type with its `type` and `kind`.

## How it works

### Building

`build.mjs` builds the crate for `wasm32-unknown-unknown` without features into `src/generated/` and with `--features engine` into `src/generated-engine/`. Each build runs wasm-bindgen for the web target, shrinks the module with wasm-opt when `SHIFT_WASM_OPT=1`, and writes it as base64 into `module.ts` (the engine: as `shift_wasm_bg.wasm`), dropping the glue's fetch-by-URL fallback so bundlers emit no stray copy. `src/index.ts` decodes its module and calls `initSync` at import. The editor's wrappers in `lib/wasm/` intern names, pack inputs, and unpack results; they hold no rules of their own.

Every `@shift/wasm` app build task (`build`, `build:debug`, `build:e2e`) runs the script, and the turbo test tasks depend on `build`.

The Nix dev shell provides `wasm-bindgen-cli`; CI jobs install the version `Cargo.lock` pins with `.github/actions/wasm-toolchain` (`taiki-e/install-action`). Updating wasm-bindgen means changing the crate pin, the Nix package, and `Cargo.lock` together. wasm-opt needs no install: `pnpm install` brings it with `@shift/wasm`'s `binaryen` devDependency, so updating it is a `package.json` change.

### Choosing a route

Rust owns every rule the font compiler or format decides, and the editor and export must agree on it. When the editor needs one synchronously, ask: if the Rust changed tomorrow, would the TypeScript disagree with export without anything failing?

- **A rule goes through this module.** Ordering, reversal, structure matching, precedence, model construction: anything a compiler decides. It is a plain-data function in shift-font that native projection calls too, exported here and called through a wrapper. There is no TypeScript copy, not even as a fallback for when the module is missing. A function that returns "no answer" (structures that don't match, a location outside the model) lets the caller fall back to a different rule's output, never to a TypeScript version of the same rule.
- **Arithmetic with no decision in it may stay in TypeScript.** Weighted sums, matrix application, and bounds over live buffers have nothing that can drift beyond float rounding. Each one still gets a test against the Rust (see Reference tests).
- **A rule stays in TypeScript only when measured.** On a per-frame path, calling here costs packing, copying in and out, and unpacking. A rule that stays in TypeScript for that reason needs a measurement of both paths on the same workload, boundary packing included, and a reference test, and gets a line under "What stays in TypeScript" giving the reason. A guess that the boundary is too slow is not a reason; at tens of points a call can cost less than the objects the TypeScript allocates.
- **Split mixed code at the rule.** When one function both decides (which points pair up) and computes (their weighted sum), the deciding part comes here even if the arithmetic stays in TypeScript.
- **One side owns each piece of data.** A number layout is documented once, on the Rust export, and the editor's wrapper packs and unpacks it with no logic of its own. Identity (contour and point ids, output order) is decided on one side, and the export's doc comment says which. Rust returns numbers in a stated order, and the wrapper attaches the ids that order implies.

### Moved from TypeScript, measured

Per-frame geometry now runs here, through glyph-state, with no TypeScript copy and no reference test: segments and tight bounds (`segmentContour` → `contourGeometry`, shift-font's `SegmentIndexIter` and `SegmentIndices::bounds`) and component placements (`composeTransform`, `decomposeMatrix`, shift-font's `DecomposedTransform::to_matrix` and `from_matrix`). Measured on the M4 against the TypeScript they replaced: segments plus bounds of one contour 0.041 against 0.034 ms at 326 points and 2.4 against 1.9 ms at 20,001 (the Rust call alone is 0.47 ms of that); a placement 0.21 against 0.03 µs to compose and 0.30 against 0.01 µs to decompose. Edits themselves, previews included, run in the window's engine (`engineApply`, `enginePreview`). Axis mapping and its inverse are shift-font's `map_location_with_bases` and `unmap_location_with_bases`, and interpolation weights `InterpolationBasis::weights_at`, through the engine's reads for the open document and the stateless `Variation` calls otherwise. New glyph and anchor names come from the engine too (`engineNextGlyphName`, `engineNewAnchorName`, over shift-font's `naming`). Pasted SVG path data is parsed by shift-font's `svg_path::contours_from_svg_path`, which the command line uses too, through `svgPathContours`. It is exported from the engine module only, which it grows by 38.9 KB (23 KB gzip, 1.3%); in the module every window embeds it would have added 41.7 KB, 19%.

### What stays in TypeScript

Nothing at present. Blending glyph geometry (`interpolateSourceValues`) was the last: it runs every frame over the live coordinate buffers, drag previews included, which the window's engine does not hold, so the editor packs them into one array and calls `blendSourceValues` (shift-font's `interpolation::blend_values`, the sum `GlyphInterpolation` resolves with). Measured on the M4 with the packing included, against the TypeScript loop it replaced: 0.0038 against 0.0055 ms for 326 points and two sources, 0.021 against 0.020 ms at 5,000, and 0.161 against 0.160 ms at 50,000 (0.279 against 0.293 ms with four sources).

### Reference tests

A rule that stays in TypeScript is tested against the Rust directly, not against a fixture Rust writes: the test builds its inputs in code, runs the TypeScript and the Rust on each, and compares. Nothing stays in TypeScript today, so there is no reference module: axis mapping, the last rule compared that way, runs in Rust on both paths, and its cases are Rust tests of the stateless calls (`variation.rs`). A rule that has to stay in TypeScript again brings back a test-only `reference` feature, built into a module of its own that never ships, whose exports convert inputs, call the shift-font function native callers use, and convert back.

## Workflow recipes

### Adding a rule

1. Make the rule a plain-data function in shift-font that native callers use too.
2. Add a method to the module area's `#[pack::interface]` trait (or a new trait with its `<trait>Request` export), taking and returning `#[derive(Pack)]` types: structs this crate owns, or shift-font's behind `#[cfg_attr(feature = "pack", derive(pack::Pack))]`. Implement it on the type that answers the trait. Cold calls go the same way.
3. Run `pnpm build:wasm` (turbo rebuilds it on its own before typecheck and tests), which writes the trait's class into `@shift/wasm/protocol`. A new trait also needs its class built in the entry point of the module that answers it (`packages/wasm/src/index.ts` or `engine.ts`).
4. Wrap the call in `packages/editor/src/lib/wasm/` only where the editor needs a different shape (`followingPlacements` turns decomposed transforms into matrices), and delete the TypeScript copy and its oracle.

## Gotchas

- **Running vitest directly skips the build.** Running vitest from a package directory or an editor test runner does not go through turbo, so after changing shift-font or this crate the modules are stale until `pnpm build:wasm` runs. The root `pnpm test`, `pnpm test:desktop`, and `pnpm check` rebuild them.
- **A missing module fails at import.** A fresh clone has no `src/generated/`; anything importing `@shift/wasm` fails to resolve it until the first build.
- **The protocol is written by a check, not the wasm build.** The pack macros write their fragments only when `PACK_TS_DIR` is set, so `protocol.mjs` runs `cargo check -p shift-wasm` in its own target directory (`target/pack-types`), cleaning a crate whose fragments are missing so its macros expand again. Running vitest directly after a Rust change leaves `@shift/wasm/protocol` stale until `pnpm build:wasm`, like the modules.
- **The workspace clippy run skips the engine's exports.** `cargo clippy --workspace` builds without features, so CI's `rust-check` job lints `--features engine` for wasm32 in its own step.

## Verification

```bash
nix develop --command cargo test -p pack -p shift-wasm --lib  # packing round trips and request dispatch
nix develop --command pnpm build:wasm                # build src/generated and src/generated-engine
nix develop --command pnpm check                     # tests build every variant first; typecheck builds their declarations
nix develop --command cargo clippy -p shift-wasm --target wasm32-unknown-unknown -- -D warnings

```
